# TUI の設計メモ

[English](../tui.md)

端末で動く FE: `amonhen tui`。アプリが届かない所（SSH のセッション、デスクトップのないマシン、エディタの横の端末）のためのもので、目指すところはアプリと同じ: 画面のどこも git を待たない。

状態: 段階 T1 と T2（History・選んだコミットの詳細と差分・スクロール・`--snapshot`・`--measure-scroll`）と、T3（Working Copy の一覧と差分・ファイル、hunk、行ごとの stage・discard・メッセージの欄・commit と amend・変化の知らせ）、T4 の大半（Branches・Remotes・Tags のあるサイドバーとその絞り込み、History の検索、祖先の強調、キーの一覧）、T5 のふだんの操作（fetch・pull・push・checkout・新しいブランチ・merge・rebase・stash・undo、止まった操作の続行と中止）、T6 の一部（コンフリクトの解決、Stashes）を作った。残りは設計。

## 概要

- Rust で、ratatui（セルのバッファとフレームの差分。`ratatui-core` と `ratatui-crossterm` だけ。画面はどれも自前で描くので、部品の crate は要らない）と crossterm（入力・色・代替画面。Unix と Windows）を使う。
- エンジンの一部にする: `amonhen tui [<path> | ssh://host/path | daemon:<path>]`。実行ファイルは増やさないので、エンジンのあるホストには TUI がある。
- コアへは FE 向けの窓口（`amonhen-front`、[front.md](front.md)）だけを通る。CLI と同じで、手元のパスは同じプロセス、`daemon:` と `ssh://` は共有の daemon。History はアプリと同じ永続キャッシュを使う。
- キーボードが主。マウスは補助（ホイール・クリックで選択・仕切りのドラッグ）。
- 画面・名前・文言は [ux.md](ux.md) に従う。端末でアプリと同じにできない所は TUI なりの形にし、[frontends.md](frontends.md) に TUI の列を足してそこに書く。

作らないもの:

- アバター、窓の背景と画像つきのテーマ、GitHub と AI の機能、設定のページ（設定はアプリと `amonhen run` で変える。TUI は読むだけ）。
- ドラッグ＆ドロップ。アプリがドラッグで行う操作（merge・rebase・並べ替え）は、選択に対する命令にする。
- Unicode の罫線が出ない端末と、256 色に満たない端末。

## 置き場所

| 部分 | 場所 | 補足 |
| --- | --- | --- |
| TUI | `crates/tui`（`amonhen-tui`、ライブラリ） | `Arc<dyn Front>` を受け取る。リポジトリをどう開いたかは知らない。`amonhen-front`・`amonhen-layout`・`amonhen-model`・`amonhen-projection`・ratatui・crossterm に依存する（`amonhen-commands` は T4 から） |
| 入口 | `crates/cli` のサブコマンド `tui` | ほかのサブコマンドと同じ開き方（`open_repository`）で開き、窓口を `amonhen_tui::run` に渡す |
| 切り替え | `amonhen-cli` のフィーチャー `tui`（既定で入れる） | `--no-default-features` で作るターゲットごとの検査では外れる（`syntax` と同じ） |
| セルのグラフ | `amonhen-projection::terminal` | いま `crates/cli/src/graph.rs` にある、レーンを列に詰める処理と罫線の格子をここへ移し、`amonhen log` と TUI が同じグラフを描く。CLI は格子を ANSI の文字列にし、TUI は ratatui のバッファに書く |

コアに端末のコードは入れない。最初の数段階では `amonhen-front` に命令を足さない（TUI に要るものは、VSCode 拡張と CLI のためにもうある）。

## 構造

```
 crossterm のイベント ─┐
 front.subscribe ──────┼─▶ 1 本のチャネル ─▶ メインスレッド: 状態を更新 ─▶ 変わっていれば描く ─▶ 端末
 ワーカーの答え ───────┘                           │
                                                   └─▶ ワーカー: front.call（待つ）。古くなれば取り消す
```

- メインスレッドが状態と端末を持つ。1 本のチャネルで待ち、入力・ワーカーの答え・変化の知らせ・タイマー（何かが動いている間と、検索が進み具合を出す間だけ）で起きる。何も変わらなければフレームを描かない。
- `Front::call` は答えを待つので、呼び出しはすべてワーカースレッドで行い、答えはチャネルで返す。要求の種類ごと（History の行・差分・status・検索）に世代を持たせ、今より古い答えは捨てる。走っている検索は `call_until` で取り消す。
- 状態はただのデータ（どの画面か・選択・スクロールの位置・下に書くキャッシュ）。描画は状態の関数（ratatui の想定どおり）。部品の木は持たない。
- フレームは synchronized update（`CSI ? 2026`）で包んで書く。対応する端末ではフレームがまとめて出る。送るのは、変わったセルだけ。
- フレームの出力は自前（`canvas`）。`ratatui-core` のセルのバッファと ratatui の crossterm のバックエンドの上に作り、ratatui の `Terminal` は使わない（`Terminal` は、フレームごとにすべてのセルを消して組み立て直し、すべてを比べる）。イベントは、何を変えたかの印をつける: すべてか、1 つのペイン（サイドバー・メインの画面・詳細と差分）。ペインだけになるのは、そのペインしか変わりえないもの: ペインの上のホイール、History の選択の移動、詳細のスクロール、History の行・祖先・コミット・構文の色を埋める答え。印のついたペインだけを消して組み立て直し、比べる。一番上と一番下の行は、どれかを描き直すたびに描き直す。キーの一覧はペインに重なるので、出している間はすべてを描き直す。ここにないものは、すべてに印をつける（分類していないイベントで、ペインが古いまま残ることはない）。

### History

- `history` が番号つきの History と行数を返す。更新が来ても、スクロール中はその番号が使える。
- 行は `historyRows` で範囲ごとに取る（ノード・エッジ・ID・時刻・件名と作者）。見えている範囲の前後（数画面ずつ）の行を持っておき、端に着く前に次の分を頼むので、スクロールの 1 歩は手元のデータだけで描ける。まだない行（遠くへ飛んだ直後）は、答えが来るまで空のまま。頼むのは一度に 1 つで、次に何を頼むかは答えが返ってから決める。
- 1 コミットは必ず端末の 1 行。行と画面の位置は引き算で求まり、ページ単位のスクロールで行の高さを測らなくてよい。`amonhen log` がコミットの間の「つなぎの行」に描いている曲線は、コミットの行に描く: コミットから出る曲線はそのコミットの行で曲げ、親に入る曲線は親の行で曲げる。隣の行へまっすぐつなぐ曲線は、first-parent なら親の行（ブランチが分かれた所へ戻る形）、マージなら子の行で曲げる。ほかのレーンを横切る線は `┼` になる。
- グラフの列は、要るだけ取る。上限は幅の一部（既定で 3 分の 1）。通るだけのレーンは、`amonhen log` と同じく細い 1 列にまとめる。
- ref の札は `refs` から取り、コミットの ID で行に付ける。選んだコミットの祖先は `historyLineage` で強調する（ほかを薄くする。アプリと同じ）。`historyLineage` は History 全体について答える（行ごとに 1 ビット。linux で 185 KB）。アプリは描く範囲までしか求めない。頼むのは 1 つずつで、SSH 越しでの重さは測っていない。
- 検索は History の検索の書き方で `historySearch` を使い、見つかった分から出す（`historySearchPartial`）。作ったもの: `/` で一番下の行に語を打つ。検索は専用のワーカーで動き、次の検索を始めるか Esc でやめると取り消す。合った行は件名に色がつき、一番下の行に、選んでいるのが何番目かと合った数を出す。結果は検索が終わってから出す（途中の結果はまだ）。History を読み直すと、検索し直す。

### 差分

- `commitDiff` と `workingDiff` は行のレコードと文字の表を返す。TUI は答えをそのまま持ち、見えている行だけをそこから描く（行ごとに文字列を作らない）。
- 変わった語は `highlights` の区画を使う。構文の色は差分を出してから頼み（`diffSyntax`）、届いたら塗る。どちらの位置も、窓口がどの FE にも渡すとおり、行の中の UTF-16 の単位。
- 詳細は、History の行とは別のワーカーで読む。大きなコミットの差分を待つ間も、スクロールは止まらない。頼むのは 1 つずつで、答えが届いたときに選択が動いていたら、その答えを捨てて、選んでいるコミットを頼む。
- 長い行は枠の端で切り、差分を横に動かせる（`h` `l`。左の端では、`h` は一覧へ戻る）。タブは 8 の倍数まで進める（端末の `git diff` と同じ）。
- 色は端末に従い、アプリで選んだテーマには従わない（テーマはアプリの設定で、コアのものではない。端末には、使う人が選んだ色がすでにある）。構文の種類と `+` `-` の印は、端末の 16 色。追加・削除の行と変わった語の地の色は、256 色の決まった色で、暗い組と明るい組を `COLORFGBG` で選ぶ（端末が知らせなければ暗い組）。
- 最初は 1 列（unified）だけ。左右に並べる表示は 160 桁ほど要るので後にする。

### 変化

`front.subscribe` が変化のビット（refs・index・作業ツリー・config）を届ける。続けて来たビットはまとめ、ビットが指すものだけを読み直す（index と作業ツリーなら `status`、refs なら `refs` と `history`）。画面の History は新しいものができるまで番号を保ち、できたら選択をコミットの ID で引き継ぐ（`historyRowOf`）。refs が変わると History をその場で読み直し、同じコミットを選び直す（`historyRowOf`）。行は、届くまでは今も空になる。TUI 自身が stage した後は、知らせを待たずに状態を読み直す。

## 画面

```
 amonhen-standalone  main ↑2 ↓0                                   ⟳ Fetching origin…
┌ Workspace ─┬ History ───────────────────────────────┬ a1b2c3d4 ──────────────────────┐
│ Changes  5 │ ● ─╮  (HEAD → main) Fix the graph  Ann │ Fix the graph                  │
│ History    │ │  ●  Add a test               Bob  2d │ Ann <ann@example.com>  2d ago  │
│ Stashes  2 │ ●─╯  Merge branch 'topic'      Ann  3d │                                │
│ Branches   │ ●    Bump the version          Ann  5d │ M src/graph.rs         +12 -3  │
│  ★ main    │ ┆                                      │ A tests/graph.rs       +40     │
│    topic   │                                        ├────────────────────────────────┤
│ Remotes    │                                        │ @@ -10,7 +10,9 @@ fn layout()   │
│ Tags       │                                        │ -    let lane = 0;             │
│            │                                        │ +    let lane = trunk();       │
└────────────┴────────────────────────────────────────┴────────────────────────────────┘
 Rebase 3/7 · 2 conflicts   c continue  s skip  a abort                    ? help  : commands
```

- 端末が広ければ（140 桁ほどから）3 列: サイドバー・メインの画面・詳細。狭ければ、詳細はメインの画面と入れ替わりで開く（History では Enter か Space で入り、Esc で戻る）。さらに狭ければ（80 桁ほど未満）、サイドバーは呼んだときだけメインの画面に重ねる。作ったもの: サイドバー（26 桁）は 100 桁から出る。メインの画面と詳細は、残りが 116 桁あれば（全体で 142 桁ほど）並べ、メインの画面は 5 分の 2（少なくとも 60 桁）を使う。100 桁未満では、`0` でサイドバーをメインの画面の所に出す。
- サイドバーはアプリと同じ節（メインの画面を切り替える Workspace の行、続いて Branches・Remotes・Tags・Worktrees）と、絞り込みの欄を持つ。
- 一番上の行は、リポジトリ・今のブランチと ahead / behind・動いている処理。一番下の行は、merge・rebase・cherry-pick の途中ならその状態と操作、そうでなければ、フォーカスのある所のキーの案内。
- Working Copy はアプリと同じ 1 つの一覧で、ファイルごとにチェック（`[x]` stage 済み、`[-]` 一部、`[ ]` まだ。Space で stage / unstage）。右に差分（hunk・行ごとの stage。`stageRows`・`discardRows`）、一覧の下にメッセージの欄。
- シート（確認・Branch・Merge・Rebase・Push…）は画面に重ねる枠で、欄と文言はアプリと同じ。壊す操作は先に尋ね、Undo で戻せるかを書く。

## キー

- 移動: 矢印と `j` `k`、`g` `G`、PageUp と PageDown、`Ctrl-d` `Ctrl-u`。枠の間は `Tab` と `Shift-Tab`。Workspace の行は `1`…`5`。
- 詳細では: `[` `]` で前と次のファイル、`h` `l`（と左右の矢印）で差分を横に動かす、Esc で History に戻る。
- Working Copy の差分では行を選ぶ（`j` `k`。`[` `]` で hunk の見出しへ）: Space でその行を stage / unstage、`d` で捨てる。hunk の見出しでは、どちらもその hunk すべてに働く。一覧では `d` でファイルの変更を捨てる。捨てる前に一番下の行で尋ね（`y` で進む、ほかのキーでやめる）、Undo で戻せることを書く。T5 でシートができるまでの形。
- メッセージの欄は Working Copy の一覧の下にあり、見出しに件名の行の文字数を出す。`c` で入り、Esc か Tab で戻る。書いている間は、ふつうのキーはすべて文字になる。コミットは `Ctrl-s`（一覧からも。端末が送るなら、欄では Alt-Enter でも）。端末は Ctrl-Enter と Enter を区別できないため。一覧の `a` で amend を切り替え、入れたときに欄が空なら直前のコミットのメッセージを入れる。コミットできないときは、理由を一番下の行に出す（メッセージがない、何も stage していない）。アプリの Commit ボタンがツールチップに出すのと同じ。
- `0` でサイドバーへ（一覧からは `h` か左の矢印でも。Tab は枠を順に回る）。Enter か Space で選んでいる行を開く: Workspace の行はメインの画面を替え、ブランチ・リモートのブランチ・タグは History でそのコミットを選ぶ。`1` と `2` は、どこからでも Changes と History に替える。サイドバーが出ていないときは、一番上の行にメインの画面とそのキー、変わったファイルの数を並べる。
- `/` で検索（History。サイドバーでは絞り込み）、`n` `N` で次と前。
- `:` で命令の一覧: 共通の表（`amonhen-commands`）の操作のうち TUI にあるものを、打った文字で絞り込み、キーを横に出す。`?` でフォーカスのある所のキーの一覧。
- アプリのツールバーにある操作は 1 文字のキーを持つ（`f` fetch、`p` pull、`P` push、`b` branch、`m` merge、`r` rebase、`s` stash、`u` undo）。アプリがシートを通すものは、TUI もシートを通す。
- 操作の表のショートカットは窓のアプリ向け（`Primary+Shift+B`）で、ほとんどは端末で打てない。表に TUI のキーの列を足す（GTK の列と同じ）。
- kitty のキーボードプロトコルは、端末が答えたときだけ使う（ふつうの端末で区別できないキーのため）。これに頼る機能は作らない。

## 端末だから違うところ

- パスワードとパスフレーズ: git と ssh は端末なしで動く（端末は TUI が使っている）。TUI は `AMONHEN_ASKPASS` を、`amonhen tui --askpass` を呼ぶ小さなスクリプトにする。そのプロセスは、動いている TUI が待っているソケットにつなぎ（場所はスクリプトに書く。daemon は `AMONHEN_ASKPASS` を引き継ぐが、ほかの `AMONHEN_*` は引き継がない）、TUI がシートで尋ね、答えを返す。daemon は FE の `AMONHEN_ASKPASS` を使うので、共有の daemon が git を動かすときも同じに働く。
- コミットメッセージ: ふだんは TUI の中の複数行の欄。`Ctrl-e` で代替画面を抜け、git のエディタ（`GIT_EDITOR`・`core.editor`・`VISUAL`・`EDITOR`）でメッセージを開き、戻る。
- マウス: 取り込むと端末の文字の選択が効かなくなる（多くの端末は Shift を押しながらなら選択できる）。既定で取り込み、切るキーと設定を持つ。
- コンフリクト: 一覧にし、ファイルごとのコンフリクトを出し（`conflict`）、アプリにあるコンフリクトごと・ファイルごとの選択を使えるようにする（コアは `resolveConflict` と `takeSide` として出している）。3 ペインのエディタは作らない。`e` でファイルをエディタで開く。
- シートの前と後の絵（rebase・merge・reset）は、同じグラフのセルで描く（動きはなし）。後の段階。
- 一時停止（`Ctrl-z`）と端末の大きさの変更では、画面を戻して描き直す。`Ctrl-l` は、端末を消して画面のすべてを書き直す（中身は読み直さない）。ほかのものが上に書いて乱れたときのため。panic のときは、端末を戻してから出す。

## 速さ

[design.md](design.md) の目標を、TUI の手が届く所まで当てはめる: 端末に渡すバイト列まで。その先で端末エミュレータがすることは TUI からは変えられないので、測らない。

| 項目 | 目標 |
| --- | --- |
| キーのイベントからフレームのバイト列を flush するまで（History を 1 行スクロール） | 8.3 ms 以内。余裕を持たせ、手元のリポジトリの 200 × 60 で 1 ms 未満 |
| 同じことを `ssh://`・`daemon:` で | 同じ（行が手元の範囲にあるとき）。答えを待って止まらない |
| スクロール 1 歩のバイト数 | 測って、増えないよう保つ（SSH のセッションを通る量） |
| 起動から History の最初の画面まで | `amonhen log` より数 ms 多い程度（同じ永続キャッシュ） |

- `amonhen tui --measure-scroll` は、出力を数えるだけの先に向け、本物のイベントの経路で History をスクロールして、フレームごとの時間とバイト数を出す（アプリの同じ名前の引数）。`--measure-move` は、同じことを `j`（端に着いたら `k`）で選択を動かして行う。
- `amonhen tui --snapshot <file>` は、本物の画面と同じフレームの出力を通し（キーごとに 1 フレーム、そのキーが印をつけた所だけを描き直す）、最後のフレームを文字で書き出す。その画面が、すべてを描いたものと違えば失敗する。画面のテストはどれも、古いままのペインがないことも確かめることになる（`--size <桁>x<行>`。先にほかの画面へ進むなら `--keys <キー>`。1 文字が 1 つのキーで、改行は Enter、タブは Tab、ほかの制御文字は Ctrl と文字）。テストはこのフレームを比べるので、CI に端末は要らない。
- `--measure-scroll` も、最後の画面をすべてを描いたものと比べ、最も遅いフレームが使った CPU の時間を出す。
- フレームの組み立てと、グラフをセルに詰める所の criterion のベンチは、まだ書いていない。

### 計測の記録

T1、Apple Silicon の Mac の release ビルド、linux のリポジトリ（1,485,021 コミット）、`--measure-scroll`（600 フレーム、8.3 ms おきにホイール 1 目盛り = 3 行）:

| 大きさ | フレームの時間（中央値 / 95% / 最大） | 1 フレームのバイト数（平均 / 最大） | 行が足りなかったフレーム |
| --- | --- | --- | --- |
| 200 × 60 | 1.48 ms / 3.49 ms / 12.3 ms | 25,974 / 52,601 | 0 |
| 120 × 40 | 0.81 ms / 2.18 ms / 13.2 ms | 12,828 / 23,813 | 0 |

- 最も遅いフレームを除けば 8.3 ms に収まるが、200 × 60 で 1 ms の目標には届いておらず、最も遅いフレーム（12〜13 ms）は超えている。どこに時間がかかっているかは、まだ調べていない。
- スクロールの 1 歩で、ほぼすべてのセルを描き直している（どの行も動くため）。端末に History の領域のスクロールを送り、新しく見える行だけを送れば、バイト数も時間も減る。ratatui の `Terminal` は前のフレームを外に出さないので、`ratatui-core` のバッファの上に自前のフレームの出力が要る（T1b）。
- 最初の画面の `--snapshot` は、キャッシュがある状態の linux で 0.34 秒（プロセス全体。大半はリポジトリを開く所）。`amonhen log` とはまだ比べていない。

| 大きさ | フレームの時間（中央値 / 95% / 最大） | 1 フレームのバイト数（平均 / 最大） | 行が足りなかったフレーム |

- T1 の行とは比べられない（リポジトリが違い、200 × 60 の History は 80 桁になった）。最も遅いフレームは今も 8.3 ms を超えていて、原因もまだ調べていない。差分そのもののスクロールは、まだ測っていない。

時間がかかっている所（同じ Mac、このリポジトリ、200 × 60 でサイドバー・History・詳細。`--measure-scroll` が内訳も出すようにした）:

- セルの組み立てが中央値で 1.1〜1.2 ms、前のフレームとの差を取って書き出すのが 0.5 ms。ホイールのイベントの処理は数 µs。組み立てのうち、History の 58 行が約 0.6 ms（1 行 10 µs）、詳細が 0.4 ms、サイドバーが 0.16 ms。スクロールの 1 歩で変わるのは History だけ。グラフを列に詰める所は、そのうち 6〜8 µs。
- サイドバーと詳細のセルを前のフレームから控えておき、中身が変わらなければ写す形を試した: 組み立ては約 0.8 ms に、フレーム全体は 1.6 ms から 1.5 ms になった。状態の写しをもう 1 つ合わせ続ける手間に見合わないので、入れなかった。
- History の 1 行の中では、札・件名・作者・日付を書く所がほぼすべて（1 フレームで約 0.45 ms）。グラフの線とそのセルは 0.05 ms に満たない。ASCII の文字列を `set_stringn` を通さずにセルへ直接入れる形も試したが、測れる差は出なかった（1 フレーム 1.5〜1.8 ms で、前と同じばらつき）ので、これも入れなかった。計測はフレームの間に 8 ms 眠るので、どのフレームもキャッシュが冷えた所から始まる（実際のスクロールと同じ）。
- 最も遅いフレーム（8〜24 ms）は、1 つの所ではない: 組み立てにかかっている回もあれば、差と書き出しにかかっている回もあり、そのフレームでワーカーの答えは処理していない。スレッドが止められているように見えるが、確かめていない。
- そのため、1 ms の目標には今も T1b が要る: 動かなかった所を組み立て直さず、差も取らない。

| 大きさ | 前（1 回の中央値） | 後 | 組み立て / 差と書き出し（前） | 後 |
| --- | --- | --- | --- | --- |

| 120 × 40（サイドバー・History） | 0.61〜0.82 ms | 0.43〜0.63 ms | 0.40〜0.54 / 0.19〜0.27 ms | 0.29〜0.40 / 0.15〜0.22 ms |
| 80 × 60（History だけ） | 0.93〜1.46 ms | 0.93〜1.39 ms | 0.63〜0.93 / 0.29〜0.51 ms | 0.63〜0.89 / 0.31〜0.46 ms |

- 動かなかったペインに触らなくなり、200 × 60 のスクロールの 1 歩は History だけの分になった: この回では 1 フレーム約 0.9 ms、機械がもっと空いていたときの回では 0.70〜0.80 ms（そのとき、前は 1.29 ms）。1 ms の目標は下回るが、余裕はない。95% のフレームは 1.7〜1.9 ms（前は 2.8〜3.2 ms）。
- History が幅のすべてを使う所では、前も飛ばせるものがなく、時間は変わらない。残っているのは History そのもの: どの行も動くので、歩ごとに 58 行を組み立て直して比べる。
- 1 歩のバイト数は変わらない（200 × 60 で約 5,000）。前から、変わったセルだけだった。
- 最も遅いフレームは、スレッドが止められていた: 6〜33 ms かかったフレームが使った CPU の時間は 1.0〜1.2 ms（`CLOCK_THREAD_CPUTIME_ID`）。3 回走らせて 3 回とも。そのフレームで、TUI の中に遅い所はない。
- 端末のスクロール領域は作っていない。領域は行の全体を動かす（`DECSTBM`）ので、History が幅のすべてを使うときにしか合わない。サイドバーや詳細と並ぶ所では左右の余白（`DECSLRM`）が要り、持たない端末が多い。減るのは 1 歩のバイト数（SSH のセッションが運ぶ分）で、時間ではない: グラフの列は見えている行から詰めるので、残る行も変わることがあり、どのみち組み立て直して比べる。
- 本物の端末エミュレータで確かめた: tmux の 200 × 60 で TUI を動かし、History の選択を動かすキーと詳細をスクロールするキーを押した後の画面は、同じキーの `--snapshot` と同じ。
- 測っていないもの: 差分のスクロール。

History の行を前のフレームから持ち越す。同じ Mac とリポジトリ、前のビルドと後のビルドを交互に 5 回ずつ（上と同じく、機械は空いていない）。`--measure-move` は、`--measure-scroll` がホイールを回す所で `j` を押す:

| 大きさ | スクロール、前（1 回の中央値） | 後 | 移動、前 | 後 |
| --- | --- | --- | --- | --- |
| 200 × 60（サイドバー・History・詳細） | 0.65〜0.99 ms | 0.30〜0.56 ms | 0.56〜0.59 ms | 0.40〜0.45 ms |
| 80 × 60（History だけ） | 0.32〜0.36 ms | 0.16〜0.35 ms | 0.32〜0.45 ms | 0.16〜0.25 ms |
| 120 × 40（サイドバー・History） | 0.29〜0.84 ms | 0.24〜0.60 ms | 0.52〜0.67 ms | 0.34〜0.61 ms |

- スクロールの 1 歩で見えている行をすべて組み立て直していたが、新しく見える行のほかはずれるだけ。History は、組み立てた行のグラフより右のセル（札・件名・作者・日付）を、見えている行の 2 倍まで持っておき、幅・グラフの幅・中身が同じ間は写す。グラフ・選択・祖先の薄い色は、フレームごとに変わるので毎回描く。すべてを描いたものとの照合（`--snapshot` と計測）は、どの行も組み立て直すので、古い行が残れば失敗する。
- フレームの組み立ては、どの組でも短くなった（200 × 60 のスクロールの 1 歩で 0.44〜0.62 ms から 0.11〜0.19 ms）。比べて書くほうは短くならず、120 × 40 では長くなった（0.10〜0.31 ms から 0.14〜0.40 ms）。組み立てが払わなくなった分の一部が、そこに出ている。フレームの全体は、30 組のうち 29 組で速く、残りの 1 組（120 × 40 のスクロール）は 3% 遅い。
- スクロールの 1 歩で残っているのは、ほぼセルを比べて書く分（200 × 60 で 0.2〜0.3 ms）で、バイト数は変わらない。
- `j` での選択の移動は、スクロールの 1 歩とほぼ同じだけかかる。選択が触る 2 行だけを描き直すものは作っていない: 祖先の薄い色が少し後に届いて、ペインのあちこちの行を変える。
- この表の数字は、同じビルドでも T1b の表より小さい。機械がより空いていたためで、比べられるのは組の中だけ。

## 配布

- TUI は、エンジンを作るすべてのターゲットでエンジンに入れる。crossterm は Windows のコンソールを直接扱うので、Windows のエンジンにも入る。
- エンジンは約 0.77 MB 大きくなる（darwin-aarch64 の release ビルドで 40.28 MB から 41.05 MB、1.9%。History だけを作った時点では 0.36 MB）。そのため、SSH 先へ送るものも含め、どのエンジンにも入れる。
- terminfo も C のライブラリも要らないので、musl の静的なエンジンは静的なまま。
